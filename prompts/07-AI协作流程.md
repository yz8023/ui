# 07-AI协作流程（需求描述 / 计划 / 执行 / 审计 / Bug 定位 / 回归）

> 来源：提炼自《AI 开发的大概流程》（飞书，SpicyTater：
> https://iaadlou6fm1.feishu.cn/wiki/GLf6w38ITiH64EkkB9pceuxynRd ）的
> 「说清需求 → 整理计划 → 完成功能 → 实际检查 → 修正问题」方法，
> 条例全文见 `docs/AI开发流程与需求描述规范.md` 与 `AGENTS.md` 第 6 节。
>
> **调用方式**：按任务阶段复制下面对应模板作为消息发给 AI，把 `【】` 换成实际情况。
> 小改动只用模板一（或直接下需求）；多功能/易跑偏的任务按 一→二→三→四 的顺序走全流程；
> 遇到 Bug 用 五→三→六。不要几套模板同时发给同一个任务。

---

## 模板一 · 需求拆解（开工前，把六要素补齐）

```text
我要做：【功能一句话说明】。

先别写代码。请按下面六项帮我核对需求，缺的直接问我，不要自行假设：
1. 做什么：包含哪些字段/元素，哪些必填、格式规则是什么，
   哪些在本地就能判断、哪些必须查后端；
2. 何时提示：输入时 / 离开输入框时 / 点提交时分别要不要检查，
   提示显示在哪、改对后何时消失；
3. 接口过程：什么时候请求、地址与参数、返回字段的含义、
   等待时怎么显示、成功后怎么变、失败后怎么办（要保留已填内容、能重试）；
4. 联动关系：哪一处变了、哪些地方必须跟着变（含旧请求晚返回不能覆盖新状态）；
5. 保留项：现有【字段/校验规则/接口参数/跳转行为】中哪些不许动，逐条列；
6. 验收方法：完成后我按什么步骤亲手检查（包括填错、断网、重复点击的情况）。

如果当前项目已有相关实现，先看现有代码再回答，并说明你沿用什么、缺什么。
```

## 模板二 · 制定计划（复杂任务，先计划后执行）

```text
先阅读现有项目（按 AGENTS.md 的阅读顺序）和下面这份已确认的需求，整理一份实现计划，暂时不要修改代码。

需求：【粘贴模板一确认后的需求】

计划里写清楚：
- 这次要做哪些功能，哪些明确不做；
- 分几步完成，每一步会涉及哪些文件、改什么；
- 每一步完成后怎么检查（具体操作步骤和预期结果）；
- 功能之间有没有依赖顺序（参考手册 F 依赖图）；
- 哪些信息还不明确，单独列出来等我确认，不要当成已确定的需求。

计划只出确认版一份，后面都按这一份做。
```

## 模板三 · 按计划执行（每完成一步就停下来给验收点）

```text
请先阅读项目和已确认的实现计划，完成第【 】步：【步骤名】。

要求：
- 沿用项目已有的组件、状态与实现方式（先看权威源码再动手），保留计划里列明的保留项；
- 只改这一步涉及的文件，需要动其他地方先停下来说明原因；
- 完成后说明：改了哪些文件、每处改了什么、你实际做了哪些检查、检查结果是什么；
- 涉及接口时明确区分：哪些已接通真实接口，哪些还在用模拟数据；
- 最后给我一份人工验收清单：点哪里、填什么、应该看到什么，正常和出错两种情况都要有。
```

## 模板四 · 审计检查（换一个会话用；只查不改）

```text
请对照实现计划和最初需求，检查这次代码改动，暂时不要修改任何文件。

重点看：
- 需求有没有遗漏或做偏（逐项对照需求六要素）；
- 正常操作、填错、断网、重复点击、快速切换时的处理是否完整；
- 异步请求有没有旧结果覆盖新状态的问题；联动清空/重查是否到位；
- 有没有影响已有功能（接口参数、校验规则、跳转行为等保留项是否被动过）；
- 有没有把模拟数据当成已接通、把未验证说成已完成。

发现问题时，请给出：具体文件与位置、触发条件、实际影响。
已验证的和还需要人工确认的分开写；无法确认的明确说还需要怎么验证。
```

## 模板五 · Bug 先定位（反复修不好、或怕越改越乱时用）

```text
先不要改代码，帮我定位这个 Bug 的原因。

- 复现步骤：【一步步写清操作过程】
- 预期结果：【应该发生什么】
- 实际结果：【实际发生了什么】
- 报错原文：【完整粘贴，不要删减】
- 我的怀疑（可不填）：【】

请结合当前项目的相关代码（从触发入口顺着调用链看，不要只看我贴的片段）分析：
- 最可能的原因是什么，在哪个文件、哪段逻辑；
- 可能影响哪些现有功能；
- 建议怎么改、改哪里。

分析结论给我确认后，我再让你动手修。
```

## 模板六 · 修复与回归（定位确认后用）

```text
按已确认的原因修复这个 Bug：【粘贴模板五的结论】。

要求：
- 只处理这个问题，保留项：【字段/校验规则/接口参数/跳转行为逐条列】；
  需要改到保留项或其他功能时，先停下来说明原因；
- 修完后做两轮检查：①原问题按复现步骤验证已解决；
  ②回归受影响的原有流程，对照最初需求确认行为没有被改变；
- 汇报时分开写：已验证通过的、仍需我人工确认的、这次明确没有动的。
```

---

### 和仓库其他提示词的关系

- `00-通用开工.md` 仍然是任何任务的第一条消息（体检 + 开工表）；本文件管的是
  开工表确认**之后**，需求怎么补齐、计划怎么走、写完怎么查。
- 做具体 F 功能时，先发 `00` + 对应功能提示词（01–06），需要接口/联动/多步推进时
  再从本文件补发对应阶段的模板。
