# 诊断报告：为什么把模板给别人，成果却千奇百怪

> 诊断对象：模板仓库 `yz8023/ui`（下称 ui）与照着它做、反复返工的 `yz8023/mt-lun-tan`（下称 mt）。
> 方法：两边代码、Manifest、构建配置、提交历史（ui 至 36a29cc、mt 至 v5.81/d380cdc）逐项对照。
> 结论先行：**不是某一个人「学不会」，是模板本身存在 6 个结构性缺陷，任何执行者（人或 AI）
> 都会被迫即兴发挥，即兴发挥必然各不相同。** mt 的返工史就是这 6 个缺陷的完整实证。

---

## 一、缺陷清单（按危害排序）

### 缺陷 1：同一功能有两三套互相矛盾的实现，没有标注谁说了算 ⭐最致命

换图标一个功能，仓库里有三份说法：

| 出处 | Manifest 结构 | 图标套数 | 组件命名 | 持久化 |
|---|---|---|---|---|
| `素材库/应用图标切换/`（+示例 App 实际在用的） | MainActivity **不带** LAUNCHER，3 个 alias 承担入口 | 3（冰蓝/星夜/珊瑚） | `.icon.Default/.Galaxy/.Coral` | 不存，读组件真实状态 |
| `素材库/桌面图标动态切换/` | MainActivity **本体带** LAUNCHER + 1 个 alias | 2（经典/新） | `.MainActivityIcon2` | SharedPreferences 存 `app_icon_variant` 整数 |
| `素材库/主题色配置与切换/`（含其代码里的图标卡） | 又写了一遍 MainActivity 带图标 + alias | 2 | 同上 | 同上 |

三份文档都自称标准做法，README 里还并列推荐。执行者必须三选一（或混搭），
选错/混搭的表现就是：双图标、无图标、点了没反应——然后开始怀疑人生、推翻重选。

**mt 实证**：mt 在这两套结构之间横跳了至少三轮——
v5.65 用「全 alias」方案且把组件名写错成 `_comiis.MainActivity` 导致第二个图标失效；
v5.69 改「MainActivity 本体=默认 + alias」并宣称「与 pan-x 1:1」；
期间还得出过「adaptive 图标有强缓存、必须用裸 PNG」这种与模板现行方案相反的结论，
图标载荷在 vector / PNG / adaptive 之间来回换。每一轮都有理有据，每一轮都和上一轮不兼容。

**修复**：已确立 F01 为唯一权威（示例 App 在用、真机验证过的那套），
另两处加了合并横幅（见 `素材库/桌面图标动态切换/实现方案.md` 顶部与手册 F02）。

### 缺陷 2：素材库镜像代码多处是坏的，抄了也编译不过 ⭐最致命

`素材库/*/代码/` 不参与 CI 构建（CI 只编 `android/`），坏了没人发现。实查：

| 文件 | 坏法 |
|---|---|
| `素材库/应用图标切换/代码/应用图标切换器.kt` | 对象已改名 `应用图标切换器`，同文件的选择器却还在调用英文名 `AppIconSwitcher`（不存在）；预览图资源也与示例工程不一致（示例用 `R.drawable.ic_launcher_foreground*`，镜像写 `R.mipmap.*`，而提交 71d5731 恰恰是修「用 mipmap 自适应资源当预览会崩」） |
| `素材库/主题色配置与切换/代码/主题配置屏幕.kt`（911 行） | 声明的是 `object 主题控制器` / `class 设置仓库`，文件内却通篇调用 `ThemeController` / `SettingsRepository`（不存在）；且文末 `seedColorScheme` 是个写着 TODO 的占位实现（直接返回默认深/浅色），文档却宣称已实现 HCT 种子色生成 |
| `素材库/桌面图标动态切换/代码/桌面图标切换器.kt` | 几乎缺失全部 Compose import，`R`、`IconVariantOption` 等引用无从解析 |
| `素材库/玻璃常用组件/代码/*.kt` 与其他素材 | 组件改了中文名（`主按钮`、`紧凑开关`…），但`网络壁纸`、`主题导入导出`、`权限`等镜像文件 import 的还是英文名 `PrimaryButton`、`GlassTextField`…；在镜像集合内部互抄必断 |
| `素材库/液态玻璃主题/环境要求.md`、`底部导航栏/环境要求.md` | 写的 shapes 还是 `0.1.1`，示例工程实际是 `shapes-android 1.2.0`（`gradle/libs.versions.toml`），照文档装依赖会对不上 |

对照结论：镜像集合里被引用却**从未在镜像中声明**的名字至少有
`AppIconSwitcher / ThemeController / SettingsRepository / PrimaryButton / SecondaryButton /
GlassTextField / SegmentedTabs / AppSettingsState（镜像内无此文件）` 等一串。

后果链是固定的：**抄 → 编不过 → 执行者自己改名/补实现 → 每个人补法不同 → 成果分叉**。
而且执行者会误以为「是自己理解错了」，不会想到是模板坏的（mt 的 CHANGELOG 里满是这种自我检讨式返工）。

**修复**：本次已修复 F01 镜像文件使其与权威源码一致；其余坏点在本报告与手册中逐项标出，
并新增 `scripts/check-template.py` 做镜像漂移/未声明引用/重复声明的提交前检查（见文末）。

### 缺陷 3：没说清「玻璃是 Compose 专有的」，View 项目照抄必然翻车 ⭐mt 的主战场

模板通篇用「复制即用」「与 Compose 无关（仅图标那节的语境）」的口吻，
但液态玻璃的真相是：

- 真玻璃 = `io.github.kyant0:backdrop-android` 在 **Compose 图层树**里录制 backdrop 再采样/模糊/镜头折射，
  根部接线（`AppRoot.kt` 的双层 `rememberLayerBackdrop` + `CompositionLocal`）全是 Compose 机制；
- View（XML+Java）体系**没有等价 API**。宿主若是 View 项目，只有「迁页面到 Compose」或「截图模糊做磨砂近似」两条路，
  原模板对这件事**只字未提**，更没有给 View 项目准备任何替代实现或命名规范。

**mt 实证**（一个 Java+View 论坛 App，`build.gradle` 里至今没有 Kotlin/Compose 插件）：

| 版本 | 尝试 | 结果 |
|---|---|---|
| v5.69–v5.77 | 在 View 里自研 `BackdropCache`（截图缓存）+ `GlassPanelDrawable` 近似采样，逐常量对齐 Compose 参数 | 能出「磨砂感」，但折射/采样本质不同，底栏首页不可达、胶囊被裁剪、滑杆不跟手等反馈不断 |
| v5.79（2608e5c） | 引入 Kotlin 2.3.10 + Compose，只把底栏换成 ui 原版 `LiquidBottomTabs` | 采样到的只是极光层（页面内容是 View，录不进 Compose 图层），且全 App 为一条底栏背上整个 Compose 运行时 |
| v5.80（a5b0ba6） | **整版回退**：删掉全部 Compose 代码（-1120 行），宣布「移除液态玻璃」 | —— |
| v5.81 | 两套界面并存，玻璃线事实上搁置，CHANGELOG 写明「从零重做玻璃需要单独规划」 | 至今未「学会」 |

16 个版本（v5.65–v5.81）里大半在为图标和玻璃返工。这不是执行力问题：
**模板从未告诉过他「你的项目学不了真玻璃，只能选近似并改名」**，于是他只能一轮轮试错。

**修复**：`docs/00-新人入口-先读这个.md` 增加技术栈体检与路线 C 分流；
手册 F03 写死三路线与命名规范；`prompts/03-液态玻璃-View项目先看这个.md` 给了开工前必须确认的话术。

### 缺陷 4：没有给 AI 的说明书，也没有「不许发明」的约束

mt 的提交者是 AI 代理（提交作者 `arena-agent`、PR 来自 `arena/*` 分支），
mt 仓库自己有 `AGENTS.md`，而 **ui 仓库此前没有 `AGENTS.md`、没有提示词、没有验收标准**。
把仓库地址丢给 AI 时，AI 只能：挑一份顺眼的实现 → 抄不动 → 自行改名/换机制/近似 →
用「已完成，效果近似」汇报。没有验收清单，就没人（和 AI）知道「做到什么程度才算对」，
「看起来差不多」就成了交付标准，做偏了也发现不了。

**修复**：新增仓库根 `AGENTS.md`（阅读顺序、开工表、8 条红线、汇报格式）、
`prompts/` 全套复制即用提示词（每个提示词内含文件清单、禁止事项、验收与汇报要求）。

### 缺陷 5：文档与代码长期漂移，且示例工程内部也有「双份实现」

- `HANDOVER.md` 停留在「5 个素材文件夹、只产 debug 包」的旧状态，README 已是 12+ 功能、含 release 流程；
- 示例工程里引导页有两份（`OnboardingScreen.kt` 218 行与 `欢迎引导屏幕.kt` 347 行），
  `MainActivity` 实际用后者，前者 import 了却没用——后来者根本分不清哪份是现行版；
- `素材库/状态反馈组件/代码/状态反馈组件.kt` 与 `素材库/玻璃常用组件/代码/反馈组件.kt` 内容重复，
  两个一起抄会重复声明编译失败，文档未提示二选一；
- 主题在示例里其实有两套体系并行（`LiquidUITheme` 的 7 色 Palette 体系 vs YunX 的
  `ThemeController` 动态/默认/自定义体系在素材层面的残留），文档把它们写得像同一套。

**修复**：在手册每节标注「唯一权威源码」路径与「不要选的那一份」；在各重复点加横幅；
维护规则写进 `AGENTS.md` 第 5 节：改权威源码必须同步镜像并跑检查脚本。

### 缺陷 6：难度标注失真，误导排期与预期

README 给液态玻璃标 ★★☆「需要接一两处根代码」——那是**宿主已是同版本 Compose 工程**才成立。
对 View 宿主它的真实难度是「不可直接移植」；对低版本 Kotlin/compileSdk<36 的 Compose 宿主则是「先升级工具链」。
难度不分宿主标注，等于让接手人以为翻车是自己的问题。

**修复**：手册每节按宿主分栏标注难度（Compose 宿主 / View 宿主），玻璃类功能对 View 宿主一律标注「不可直接移植，见路线 C」。

## 二、责任划分（避免下次甩锅）

| 问题 | 模板的责任 | 执行者的责任 |
|---|---|---|
| 图标反复返工 | 三套矛盾实现并列、镜像代码是坏的、没写组件名必须用完整类名等关键细节散落在不同文档 | mt 中途改信第三方 pan-x 方案、在 PNG/adaptive 之间横跳，属于被误导后的连锁反应，不宜苛责 |
| 玻璃学不会 | 从未声明 Compose 前提，未给 View 路线与命名规范 | v5.79 只迁一条底栏、未评估整页迁移成本即动手，属于开工体检缺失——而体检表正是模板该提供的东西 |
| 成果千奇百怪 | 无 `AGENTS.md`、无提示词、无验收清单、无「不许改名/换机制」红线 | 每位执行者都在坏掉/矛盾的材料上即兴，产出必然发散 |

**一句话：先修模板，再谈执行。** 本次已随报告一并修复模板侧（见下节清单），
执行侧只需要求对方：先读 `AGENTS.md`、用 `prompts/` 对应提示词开工、按手册验收汇报。

## 四、以后把模板给别人时的正确姿势（三件套，缺一不可）

1. **仓库地址** + 指定功能编号（F 编号，不要只说功能名）；
2. **`prompts/` 里对应那份提示词**全文（或让对方 AI 先读 `AGENTS.md` 再读手册对应章节）；
3. **验收要求**：按手册验收清单逐项汇报，附编译输出与真机现象（图标类必须回桌面验证）。

只给仓库地址 = 重演本次事故，这句话请写在给对方的第一条消息里。
