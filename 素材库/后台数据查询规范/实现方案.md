# 后台数据查询规范 · 实现方案

> 对应示例 App 手册编号 **F16**，条目编号 **Q01–Q05**（Q 编号独立于手册 F 编号与 UI2 的 F 编号，
> 引用时写「Q02」，不要写成「F02」）。
> 出处与口径见同目录 `参考来源.md`，运行环境见 `环境要求.md`。

## 1. 这套规范解决什么

后台/管理端最常见的痛：**查一次数据像受刑**。条件摊满三屏、每勾一个框就打一次接口、
时间口径靠嘴解释、已选条件摊成二十个标签把结果挤出屏幕、看板只能看不能点、
查到问题还要手抄数字转给负责人。

本模块把这些问题收敛成 **四条可执行规范 + 一页样板**，并且每条都在示例 App 里做成
**真实可操作的 Compose 演示**（不是截图、不是 HTML、不是占位卡）。

| 编号 | 规范 | 一句话 |
|---|---|---|
| Q01 | 筛选分层与批量提交 | 常用外置、不常用收起；查询慢就选完一起查 |
| Q02 | 时间区间写明起止 | 快捷档位写清起止与含不含当天，超限直接置灰 |
| Q03 | 已选条件标签聚合 | 全选收成一个标签，超过阈值收成「部门 · n」 |
| Q04 | 看板下钻与明细转交 | 点柱子只看这块，就地导出 CSV 并生成交接话术 |
| Q05 | 四刀合体样板页 | 四条装进同一页且状态互相一致，可直接照抄 |

## 2. 规范条文（照着做）

### Q01 筛选分层与批量提交

1. 条件按使用频率分层：高频（时间、状态、部门）常显，低频（渠道、金额区间、仅看异常）
   收进「更多筛选」；折叠时若有已选值，入口必须显示计数徽标（`更多筛选 ·2`）。
2. 单次查询耗时 > 300ms 或条件互相牵制时启用批量提交：改条件只更新「待生效草稿」，不请求；
   出现「查询（n 项待生效）」按钮，点了才发一次请求。
3. 结果区必须回显本次生效的条件与耗时；草稿与已生效条件视觉可区分（草稿项标「待生效」），
   避免用户以为已经查过了。
4. 请求期间按钮 loading 且不可重复点击，回来前不允许发第二次；连续改 10 个条件只应产生 1 次请求。

**反例**：20 个条件全摊在页面上占三屏；每勾一个复选框发一次请求，页面转圈十几次，
用户不知道哪次是最后的结果。

### Q02 时间区间写明起止

1. 快捷区间（今日 / 昨日 / 近7日 / 近30日 / 本季度 / 近一年）每个都写明实际起止日期，
   如「近7日 10-26 ~ 11-01」，并标注口径「含首尾，共 7 天」。
2. 超出数据保留期（示例 90 天）的选项置灰不可点，就地给原因与最早可查日期，
   而不是点了之后才报错。
3. 自定义起止必须校验：起 > 止 禁止查询并说明原因；止 > 今天钳制到今天。
4. 禁止只写「近7天」这类模糊文案——含不含当天在不同人嘴里不一样，是后台最常见的扯皮来源。

**反例**：按钮只写「近7天」，两人对同一份报表数出两个数；选「近一年」点了才弹「超出查询范围」，白等一次 loading。

### Q03 已选条件标签聚合

1. 同维度全选时聚合为一个标签「全部部门 · 20」，保留可点开查看/编辑的入口。
2. 同维度已选超过阈值（示例 3）聚合为「部门 · n」，点按展开明细；≤ 阈值逐个显示，每个带独立删除（×）。
3. 标签区限高（示例最多 2 行），超出用聚合标签或「+n」承接，条件栏不许把结果区挤出首屏。
4. 删除标签即回退筛选并重算命中数；提供「清空全部条件」，清空后回到默认态。

**反例**：勾了「全部部门」，条件栏摊出 20 个小组标签占满五行，结果表格被挤到屏幕外；删条件要点 20 次 ×。

### Q04 看板下钻与明细转交

1. 每根柱子/扇区都可点，点选后详情区只呈现该维度切片：标题写明「渠道 · 直播」，
   聚合数（金额、笔数、占比）与明细同步过滤。
2. 未选中时给可操作引导空态（「点任意一根柱子，这里只看这块」），不要只写「暂无数据」。
3. 切换聚合维度时清空已选切片并说明原因，避免旧切片名与新维度不匹配。
4. 明细必须可导出：生成带表头 CSV，回显行数与体积，展示前几行预览供核对，导出给触感/文字反馈。
5. 发现问题就地转交：一键生成含维度、时间范围、金额、笔数、占比、负责人的交接文本，复制即可粘贴。

**反例**：柱子只能看不能点，想知道「直播渠道哪几笔异常」只能回去改条件重查；
查到了还得自己抄数字到聊天框，负责人问「哪天的」又要再查一遍。

### Q05 四刀合体样板页

1. 页面顺序固定：条件区（常用外置 + 更多收起）→ 时间快捷（写明起止、超限置灰）→
   已选条件标签（聚合）→ 查询按钮（批量提交）→ 结果概览 → 看板 → 下钻明细 → 导出/转交。
2. 四刀状态互相一致：标签区反映全部生效条件（含时间与部门聚合）、看板与明细只受生效条件影响、
   导出内容等于当前下钻切片。
3. 草稿与生效条件严格分离；未按查询前看板与明细保持上次结果并标注「结果为上次查询」。
4. 全链路都有回显：命中条数、耗时、累计请求次数、时间口径、切片占比——
   用户任何时刻都能回答「我现在看的是什么」。

## 4. 接线（把它接到你的项目）

1. 复制 `features/adminquery/` 两个文件到宿主项目同包路径（只改 `package`）。
2. 目录/详情页要用玻璃卡与小标题时，依赖仓库内 `GlassCard`、`SectionTitle`；
   宿主没有这两个组件时，把它们换成 `Surface`/`Text` 即可，**不要改规范逻辑**。
3. 列表接入：参考 `MaterialBrowser.kt` 的第三分区，或直接在你的入口页调用
   `AdminQueryCatalogSection(onOpen = { selectedId = it.id })`。
4. 换成真实数据：把 `AdminRows` 替换为你的数据源，保留 `AdminRow` 字段名
   （`date/dept/channel/status/amount/owner` 即 CSV 表头）。`filterAdminRows` / `aggregateAdminRows` /
   `adminHandoffText` 三个纯函数不用改；`adminRowsToCsv` **必须传文案解析器**（见下条）。
   ⚠️ `dept/channel/status/owner` 存的是**稳定英文键**（`dept_07`／`ch_live`／`st_abnormal`／`own_ch_xi`），
   不是文案：接你的真实数据时，要么让你的数据源也输出这套键并往 `AdminValueLabels` 里补映射，
   要么把四个字段改回 `String` 文案并删掉查表——**别一半键一半文案**，过滤与聚合会比较不上。
5. 真实项目里把「导出 = 复制到剪贴板」换成写文件/下载时，注意申请对应存储权限并明示路径。

## 5. 关键实现机制（照抄时别改掉）

- **草稿 / 生效双状态**：`draftNow()` 在调用点即时读取条件，`applied` 只在查询成功后写入。
  这样「n 项待生效」永远算得准，删标签后重查也不会用到旧条件。
  ⚠️ 不要把 `draft` 提成 composition 期的 `val` 再传进查询函数——那会捕获旧值（本模块踩过）。
- **批量提交计数**：`diffCount(draft, applied)` 按字段逐项比较，返回差异项数；
  按钮文案与 enabled 都由它驱动，条件没变时按钮显示「条件未变化」并禁用。
- **超限置灰**：`AdminRangePreset.range(today)` 算出真实起止，
  `start.isBefore(today - (ADMIN_RETENTION_DAYS - 1))` 即禁用；本季度按季度首日实算。
- **标签聚合**：三档规则——全选 → `全部部门 · 20`；`> 3` → `部门 · n`；`≤ 3` → 逐个。
  `QTagSpec` 把「点按（展开/编辑）」与「删除（回退筛选）」分开，别合成一个动作。
- **下钻联动**：`slice` 由 `selected` + `dim` + 结果集推导；切维度时清空 `selected`
  与导出状态并给出提示，避免旧切片配新维度。
- **键与文案的分工**：维度值一律是稳定英文键，`AdminValueLabels`（39 条）查文案；复合负责人
  `own_duty_of_dept_07` 由 `Context.adminValueLabel()` 拼 `aq_owner_duty_of`（`值班组长 · %1$s`）。
  组合体内可以直接 `stringResource(AdminValueLabels.getValue(key))`；`buildList`／`remember`／`onClick`
  这些**非组合上下文**只能用 `context.getString(...)` 或 `context.adminValueLabel(...)`。
  看板柱子的标签原先写的是 `if (key.length > 4) key.take(3) + "…" else key`——键改英文后长度全变了，
  已改成**先解析文案再按文案长度截断**，照抄时别把这个顺序改回去。
- **导出与转交**：`adminRowsToCsv(rows, label)` 输出表头 + 行，`label` 故意没有默认值
  （默认 `{ it }` 会让漏传的调用点静默导出 `dept_07` 这种键），调用点传 `{ context.adminValueLabel(it) }`；
  `adminHandoffText` 六要素齐全
  （维度、时间范围含口径、金额、笔数、占比、负责人 + 已导出行数）。
  两者都走剪贴板 + `HapticFeedbackType.LongPress` 触感反馈。
- **委托属性不可智能转换**：`var selected by remember { ... }` 之后要查 `Map<String, _>`
  必须先 `val selectedKey = selected`，否则 `AdminChannelOwners[selected]` 编译不过。
- **判定依据不许用文案**：`AdminRangePreset` 拆成 `key` + `@StringRes labelRes`，`range()` 比的是
  `key == "yesterday"`；`aggregateAdminRows(dim)` 的 `dim` 是 `AdminDims` 里的键（`channel`/`dept`/`status`），
  文案查 `AdminDimLabels`。这两处原先都是拿中文文案当分派键——只有一种语言时看不出问题，
  加了 `values-en` 就会静默走 else 分支（昨日变成今天、看板永远按部门聚合）。

## 6. 模拟数据声明

`AdminRows` 是 600 行本地生成的模拟数据（固定种子线性同余，跨 400 天，20 个部门 / 5 个渠道 /
4 种状态），**不请求网络、不写文件**；页面上也明示了这一点。
「导出」= 生成 CSV 文本复制到剪贴板。负责人姓名（陈曦 / 林涛 / 赵敏 / 孙浩 / 周颖 / 王磊）均为虚构。

## 8. 红线

1. 演示必须是真实可操作实现，不许拿 HTML、截图、GIF 或占位卡冒充。
2. 规范条文改词要同步改 `strings.xml`（`aq_q*_rule` 等）与本文件，两处口径必须一致；条目骨架才在 `AdminQuerySpec.kt`。
3. 不把模拟数据说成真实业务数据；页面与文档都要明示「模拟数据」。
4. 引用来源必须保留出处（UP 名 + 标题 + BV 号），不得声称规范为本仓库原创。
5. 宿主接入时不许改掉草稿/生效双状态与聚合阈值逻辑后仍叫「符合本规范」。
